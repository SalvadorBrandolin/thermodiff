Code generator architecture¶

This page describes how a .model file (or a DiffPlz object) becomes a Fortran module, and how the code generator in thermodiff/codegen/ is organised. It is written for contributors who want to change the generator, for example to add a pass. The guiding rule of the refactor/perf-arch work is that a change must not alter the generated Fortran unless the change says so: see Invariants.

Overview¶

 .model text
     |
     v
 thermodiff/model/parser.py      read_sections -> RawModel
     |
     v
 thermodiff/model/ir.py          build_ir -> ModelIR (declarations, inlined
     |                           definitions, target function)
     v
 thermodiff/model/emit.py        build_diff -> DiffPlz
     |   (compile_model drives these three steps; emit_module also resolves
     |    the options with resolve_codegen_options)
     v
 thermodiff/diffplz.py           DiffPlz: symbolic derivatives
     |
     v
 thermodiff/fortran.py           to_fortran  (facade; implementation in
     |                           thermodiff/codegen/pipeline.py)
     |
     |  chain_rule option on:  thermodiff/chain.py
     |     chain_rule_derivatives(...) -> structured derivatives
     |     (NameScheme names the generated component/pair arrays)
     v
 pass pipeline                   _emit_code runs the passes of _PASSES over
     |                           one _EmitState, in order
     v
 thermodiff/codegen/render.py    definitions -> Fortran statements
     |
     v
 Fortran subroutine text  ->  emit_module wraps it in a module  ->  .f90

compile_model(text, filename, derivatives, *, preset, options, **overrides) in thermodiff/model/compile.py chains read_sections, build_ir and emit_module. emit_module builds the DiffPlz with build_diff, resolves the options with resolve_codegen_options and calls to_fortran.

to_fortran can also be called directly on any DiffPlz object, without a .model file; DiffPlz.to_fortran goes through the same function.

The yaeos wrapper path is separate from the pipeline. thermodiff/yaeos_model.py does not run any pass: yaeos_model_module takes the kernels that were already generated (name, argument list and output set of each workload, see kernel_interface) and emits a Fortran module with a yaeos model type that dispatches, with a select case on the set of optional outputs that are present, to the kernel that computes exactly that output set.

Module map¶

All modules live in thermodiff/codegen/ unless stated otherwise. The private helpers of every module are imported by thermodiff/fortran.py and by the tests.

thermodiff/fortran.py : Public facade. Its __all__ is only ["to_fortran"]. It re-exports the private helpers of the codegen modules (with noqa: F401) so that code and tests written before the split keep importing them from thermodiff.fortran. It contains no logic.

common.py : Helpers shared by the other modules: _Namer (sequential temporary names t1, t2, …), _sanitize, free and bound index analysis (_free_indices, _index_set, _order_free), _new_shared_temp, _print_expr (SymPy to Fortran text), the _DERIV_SUFFIX table, the indentation constant _INDENT and the _LoopStart symbol.

ir.py : The typed definition records (TempDef and its four subclasses), see Definition records.

extents.py : Extra dimensions. A summation over a dimension symbol other than nc (sum_m[1:ng], sum_custom(expr, m, 1, ng)) binds an index that annotate_index_ranges rebuilds as Idx(label, (1, ng)) at the start of the pipeline, so the range travels with the index. index_extent gives the bound of a loop or declaration; passes that create indices keep the range (slot_mapping, ranged_slots), and the loop passes that assume nc skip the definitions over an extra dimension. dimension_symbols finds the integer arguments of the kernel. One index label cannot be summed over two different ranges.

options.py : CodegenOptions, the option enums, the presets, validation and resolve_codegen_options, see Options.

resolve.py : Placeholder resolution. _PlaceholderResolver maps the internal functions (and their derivatives) of an expression to input arguments; _scan_atoms collects the atoms that become arguments; _select_derivatives resolves the user’s derivative selection.

symmetry.py : Symmetry helpers: _canonical_symmetric and _swap decide whether a summation body is symmetric under the exchange of two indices, _fold_symmetric_sums and the _merge_* helpers merge symmetric terms, and _symv_parts / _render_symv split and render the symmetric matrix-vector products.

hoisting.py : Invariant and affine hoisting: _hoist_invariants (loop invariants of the array temporaries and of the shared sums), _hoist_loop_invariants (definitions and outputs), _split_affine and _lowrank_bilinear.

cse.py : Common-subexpression search: _indexed_cse (array temporaries), _share_sums (summations), _common_scalar_cse and _sympy_scalar_cse (scalar sub-expressions, selected by cse_backend).

loops.py : Loop fusion and table rewrites: temporary fusion, nest fusion (_fuse_loop_nests, _fuse_sibling_tables, _fuse_component_maps, _fuse_outer_loops), _drop_pair_tables, _share_elementwise, _diagonal_from_tables, _permute_symmetric_subscripts, _split_accumulators, the column-order choices and _nest_double_sums. It is the largest module.

render.py : Turns definitions into Fortran lines. _render_definition is a functools.singledispatch function over the records of ir.py. It also holds _expand_sums (explicit do loops for the summations of an expression), output declaration and rendering, the dependency ordering of the definitions (_dependency_order), the optional-argument guards (_guard, _guarded) and the line wrapping of the signature.

sparse.py : Zero guards for sparse parameters (sparse_parameters). On plain loop nests it finds the terms of a reduction that carry an element v(a, b) of a declared parameter (split_by_factor), the tables whose every read is such a term at the same subscripts (their entries are skipped where v(a, b) = 0, and never read) and the tables whose body is a multiple of the element (set to zero there). The guards are only emitted when the skipped work calls a transcendental function, is a nested loop or enables a table guard (the operation-count guard of rule 7). Guarded definitions are replaced by SparseNest records.

storage.py : Storage of the array temporaries, used by assemble_text: their declarations (nc-sized automatic arrays by default, compile-time extents with max_nc plus the nc > max_nc guard) and, with work_array, the wrapper that carves every temporary out of one work_ array and calls the kernel body as an internal procedure (issue #10: without -fstack-arrays each automatic array costs a malloc/free per call). Neither option is a pass; the default output is unchanged.

core_chain.py : The chain-rule assembly of a scalar core (issue #13): scalar_chain_routine emits a companion Fortran routine that turns the derivatives of F(x_1..x_m; V, T) (a variables= kernel) and those of the scalars into the total derivatives of Ar. It does not use the pass pipeline: the second-order chain rule is a fixed contraction over the scalar index, so the loops are generated directly (Hessian on the lower triangle plus mirror, O(m) work per element through the per-column vector y_r,j), and the numeric tests compare it with the full-composition kernel. scalar_chain_core_derivatives lists what to request from the core and scalar_chain_inputs the arguments an output set needs. Core derivatives that vanish identically are dropped (core= finds them symbolically, zero= names them) and total_moles= scalars have no inputs; Ar and the pure core derivatives are passed through from the core. Not to be confused with the scalar_chain option, which is about a different step of the pipeline.

core_chain_workload.py : Fused workload kernels of a scalar core (opt-in, W21). scalar_chain_workload_module composes, per workload (a set of chain outputs), the to_fortran kernel of exactly the core derivatives the workload needs and the statements of core_chain.chain_fragments into one subroutine (fuse_kernel: the core derivative outputs become locals, no optional argument, no present()), and reuses the dispatcher of workload.py. The fallback is the full core plus the chain with optional outputs. It changes no existing entry point.

workload.py : The workload mode (issue #11, #15), built on top of to_fortran without touching the pipeline: one to_fortran call per output set (optional_derivatives=False) plus one with optional_derivatives=True (the fallback). parse_kernel reads the dummy list and declarations of each generated kernel, specialise_kernel rewrites a fixed-output kernel (explicit-shape dummies, NOINLINE, optionally nc as a named constant), shape_guard lists the extent checks that make explicit shape safe (the dispatcher falls back to the assumed-shape kernel when an actual array is larger than declared) and build_dispatcher emits the present() mask and the select case. The dummy lists come from the generated text, so extra dimension arguments are forwarded without special cases.

pipeline.py : The orchestration. It defines _EmitContext (immutable inputs), _EmitState (mutable state of one emission), Pass, the _PASSES tuple, the pass functions themselves (most of them thin adapters over the modules above), _emit_code (the loop over the passes) and the public to_fortran.

thermodiff/chain.py : The chain-rule step, used only when chain_rule is on. chain_rule_derivatives differentiates structurally over the summation nodes (summation_nodes, factor_sums) and abstracts component and pair functions into arrays. NameScheme carries the slot index names (ic, ia, ib) and the array prefixes (cmp, mat) of one run; DEFAULT_NAME_SCHEME is used unless the model clashes with them.

Options¶

CodegenOptions (options.py) is a frozen dataclass that groups the behaviour options of to_fortran. Each field has the name and default of the keyword of the same name. Per-call context (the DiffPlz, the derivative selection, names, integer_args, module_symbols, symmetric_params, stats) is not part of it.

  • Values are coerced in __post_init__. The enum fields accept the legacy values: ScalarChainMode (False | True | "cost" | "estimate"), SepSumsMode (False | True | "cost"), LowrankHessMode (False | True | "sym") and CseBackend ("thermodiff" | "sympy"). split_acc is None or 2.

  • sparse_parameters (default ()) is a tuple of parameter names, coerced from a string or any iterable; names that are not array parameters of the model are dropped with a UserWarning by the pass (the model is not known to validate()). Unlike the booleans it is not listed in _RULES.

  • canonical_placeholders (default True, in every preset) names the derivatives of placeholder functions by their variables: the gradient of B(n) is one argument dBdn(:) read as dBdn(i) and dBdn(j), its Hessian is dBdndn(:, :) (registered as a symmetric parameter), and mixed derivatives put the scalar variables first, sorted by name (dDdTdn for T and n_i in either order). False restores the index-label names (dBdi, dBdj, dBdidj). The generated names take part in the case-clash check of Fortran identifiers (a parameter DBDN next to dBdn raises ValueError).

  • Symmetric placeholders: idx_function("a", symmetric=(0, 1)) or symmetric_params=("a",) declare a(k, l, T) == a(l, k, T). The placeholder and its canonical derivatives without extra indices (a, dadT, dadTdT) become symmetric parameters; derivatives over n (dadn(k, l, i)) are not. As with symmetric_params, the caller must pass symmetric arrays.

  • from_legacy(**kwargs) and to_legacy() convert to and from the keyword form; from_preset(preset, **overrides) and replace(**changes) build variants.

  • validate(stacklevel=1) returns (normalised, ignored_names). It disables, in one UserWarning, the options that the generator would silently ignore for the chosen combination (the table _RULES: for example, everything that needs chain_rule when it is off, or the passes that cannot run with optional_derivatives). The only error is a split_acc other than 2 while optional_derivatives is off.

  • Storage of the array temporaries (issue #10), opt-in and enabled by no preset. work_array=True carves every temporary out of one work_ array (one allocation per call instead of one malloc/free per temporary when gfortran runs without -fstack-arrays). max_nc=N gives them the compile-time extent N so they live on the stack, behind an if (nc > N) error stop guard: a caller with a larger nc must dispatch to another kernel (a bigger max_nc or the default). A temporary larger than gfortran’s -fmax-stack-var-size (65536 bytes, max_nc <= 90 for a rank-2 real(8) array) becomes static and warns. max_nc disables work_array. No preset enables either: compile with -fstack-arrays instead (measurements in fortran.rst, “Compiler flags and storage of temporaries”).

  • Real kind (issue #9). real_kind="8" (the default) is the historical real(8) and d literals. Any other integer or kind name ("pr") turns every real(8) into real(<kind>) and every 1.5d-10 into 1.5e-10_<kind>; kind_module="yaeos__constants" also adds use yaeos__constants, only: pr to the subroutine (an integer kind needs no module, so validate() drops kind_module then). The conversion is one text pass at the end of _assemble_text (common.apply_real_kind), so the passes and the default output are untouched. Literals only change their kind suffix: the ~17 digits that SymPy prints for floats and pi are not extended, so with a quad kind those constants keep double-precision accuracy (exact integers and rationals are fine). A kind name equal to a model symbol raises ValueError. CLI: --real-kind, --kind-module, --work-array, --max-nc.

Presets are the Preset enum, with the settings in PRESET_SETTINGS:

Preset

Meaning

minimal

The legacy defaults: the output of earlier versions.

standard

The default of compile_model: chain rule (with chain_factor_sums), symmetry, nesting and sum sharing (_STANDARD_ENABLED).

fastest

Opt-in: the fastest generated code, slower generation and different last-bit rounding (_FASTEST_ENABLED plus the modes lowrank_hess=ON, scalar_chain=ESTIMATE, sep_sums=COST, split_acc=2).

to_fortran itself resolves its options in this order. The base is options if it was given, else the legacy defaults. The legacy keywords passed by the caller are applied on top, then the result is validated with a stack level that points at the first frame outside the package. An unknown keyword is a TypeError. to_fortran does not apply a preset: it keeps the legacy defaults, so existing callers produce the same output.

resolve_codegen_options(preset, options, **overrides) is the resolver of the entry points of the model front-end (emit_module, and so compile_model and the CLI). preset=None means "standard" unless options is given; passing both is a ValueError; an override of None means “not given”. The result is already normalised, and only the ignored options that the caller set explicitly are reported.

Note on "fastest" with optional_derivatives=True: the preset is meant for kernels specialised to one derivative set. With optional outputs the passes listed in _RULES for optional_derivatives are inactive; resolve_codegen_options disables them silently and emits one extra UserWarning saying that the preset applies fully only with optional_derivatives=False.

The pass pipeline¶

_emit_code is a plain loop:

state = _new_state(ctx, structured, stats, count_scalar, opts)
for stage in _PASSES:
    if stage.enabled(opts):
        stage.run(ctx, state)
return state.text

  • _EmitContext is a frozen dataclass with the resolved inputs (the DiffPlz, the selected derivatives, names and extra arguments).

  • _EmitState is a mutable dataclass (eq=False, so identity semantics) with everything the passes share: opts, the resolver, the namer, the outputs in their successive forms (outputs, staged, prepared, all_exprs), the definition pools (component_array_defs, array_defs, sum_defs, cse_defs), the signature data and, at the end, text. Passes mutate it in place.

  • Pass is a NamedTuple(name, enabled, run). enabled(opts) is the option-level gate and returns a bool; gates that depend on data stay inside run. run(ctx, state) returns None.

  • _gate(name, *, unless_optional=False, with_param_symmetry=False) builds the gate of a pass that depends on one option flag; it raises ValueError if name is not a CodegenOptions field.

The docstring of each pass function carries its S<n> step label, which shows the position the pass held in the original monolithic function.

sparse_guards is the only pass that no preset enables: it needs sparse_parameters (or a sparse attribute in a .model). It runs last among the passes that rewrite definitions, so it only sees what the loop passes left as plain loop nests.

split_acc is None or 2; a gate built with _gate("split_acc") is on when it is 2. The Implementation column lists the modules whose helpers the pass calls; the pass function itself is always in pipeline.py.

Two properties of the order matter:

  • scan_signature runs before every sharing pass. After the CSE the temporaries would appear as parameters.

  • render_bodies is the last stage that draws names from the namer (render-time temporaries of the expanded sums), and the sharing, hoisting and fusion passes draw names in the order of the table. tests/codegen/test_pipeline_passes.py checks both.

With scalar_chain="cost", to_fortran runs _emit_code twice (with and without the scalar chain) through _generate_cost and keeps the output with the lower scalar_operation_count; each run has its own state.

Definition records¶

ir.py holds the typed records of the temporaries. A TempDef is one temporary: target is assigned body inside loops over the free indices and the reduction limits (tuples (index, low, high)). The optional annotations are mirror, mirror_sum, colsum, colmajor, symv, symv_acc, factored and acc; None means absent, any other value (False included) means present. The records replaced string-keyed dicts and keep their semantics: they are mutable, compare by value and are unhashable. present_keys() reports the present annotations under the old key names and copy(**changes) returns a shallow copy.

Extra scalar variables¶

DiffPlz(..., variables=[B, D]) adds derivatives with respect to scalar symbols (dB, dB2, dBdD, dBdT, dndB …). The vocabulary and the parsing live in derivatives.py (scalar_derivative_specs, resolve_derivatives(scalar_variables=...)); their attributes carry the prefix var_ (var_dBdD) so that they never clash with the thermodynamic ones and are stored in DiffPlz.scalar_derivatives. In the generator they are ordinary outputs: common._deriv_suffix gives the output name and common._emission_order puts them after the thermodynamic ones. The chain-rule step (chain.py) only sees the thermodynamic attributes; the scalar ones always come from the plain DiffPlz derivatives, and their placeholders resolve as usual. The recipe for models written as a scalar core is in the Fortran page of the documentation, and its assembly step is generated by core_chain.py. Without variables nothing changes (golden byte-identical).

resolve._PlaceholderResolver warns (once per placeholder) when a placeholder has an expression argument, since the caller then has to supply total derivatives.

Invariants¶

Every change to the generator must respect these rules.

  • Byte-identical output. tools/check_golden.py --tier fast|full|complete -j N regenerates a tier and compares it with the stored golden; exit status 1 on any missing, extra or different file. fast is the quick check before a commit, full skips the slow cases, complete is everything. Do not edit the golden to make a change pass: find out why the output changed.

  • Determinism. Generation must give the same text for the same input. The golden records the PYTHONHASHSEED it was written with; run the generator with the same value. Keep the existing ordering (sp.default_sort_key, dict insertion order); never iterate a plain set of SymPy objects where the order reaches the output.

  • Namer order and count. _Namer numbers the temporaries by call order, so adding, removing or reordering a call changes every later tN. tests/codegen/test_pipeline_pins.py pins the SHA-256 of the Fortran text and of the names the namer created.

  • Identity versus value equality. _EmitState is eq=False and the helpers compare pools, namer and arrays by identity. The records of ir.py compare by value and are unhashable. Do not replace one by the other, and do not use records as dict keys or set members.

  • Per-call caches. Caches are local to a call and passed explicitly. There are no module-level caches on SymPy expressions (no functools.lru_cache on them).

  • No global state. Generation is re-entrant across interleaved calls and threads; tests/test_reentrancy.py generates the same cases alone, interleaved, after a failed call and concurrently, and requires the same text. Options are immutable; do not add mutable module globals.

  • Function size and complexity. tests/codegen/test_function_lengths.py limits functions to fifty code lines and bounds the cyclomatic complexity (10). Split a function that grows instead of raising the limit.

  • Strict typing. tox -e typecheck runs mypy in strict mode over thermodiff/codegen. New code needs complete annotations.

  • Style. Black (line length 79), flake8 and NumPy-convention docstrings (tox -e style,docstyle). Do not mix refactoring, optimisation and formatting in one commit.

How to add a new pass¶

The steps below add a pass my_pass, gated by an option my_option.

  1. Option. Add the field to CodegenOptions in options.py, with a default that keeps today’s output (normally False). If it takes a mode instead of a flag, add an enum and a coercer in _COERCERS. Add a keyword-only parameter with the same name and default to _emit_code in pipeline.py: to_fortran’s public signature is built from those parameters, and _emit_code receives the options as **opts.to_legacy().

  2. Validation. If the option has no effect in some combinations (for example, it needs chain_rule or cannot run with optional_derivatives), add its name to the matching _Rule in _RULES, so validate() disables and reports it.

  3. Presets. Decide for each preset. minimal stays empty. Add the name to _STANDARD_ENABLED only if the pass is meant for the default; add it to _FASTEST_ENABLED if it belongs to the fastest set. A change to standard changes the output of every .model compile, so say so in the commit.

  4. Pass function. Write the transformation as a function with explicit inputs and outputs in the module that owns the technique (cse, loops, hoisting, symmetry), without module state, and a thin adapter in pipeline.py that reads and writes _EmitState. The adapter does not hold state of its own and draws names only from state.namer.

  5. Register it in _PASSES at the right position. Place it after the passes whose output it reads and before those that must not see its result. If it calls the namer, its position among the namer-using stages fixes the numbering of every later temporary.

  6. Tests. Update EXPECTED_ORDER and the gate expectations in tests/codegen/test_pipeline_passes.py, add unit tests for the pure function, and run the pins (tests/codegen/test_pipeline_pins.py). With the option off, the golden must not change; with it on, add or extend a golden tier and explain the expected difference.

  7. Docs. Add the pass to the table above, in the position it has in _PASSES.

# thermodiff/codegen/options.py -- field of CodegenOptions
    my_option: bool = False

rewrite_definitions stands for the pure function in loops.py (or the module that fits); it takes the pool and the namer explicitly and returns the new pool. The attribute names of _EmitState are listed in its docstring.

Benchmarks and profiling¶

benchmarks/td_bench holds the generation variants and the derivative workloads. registry.py is the single source of truth for the variants: an ordered tuple of stage(key, base, **delta) entries, each naming its parent and only the settings it changes, plus the immutable alias map; to add a variant, append a stage. hooks.py builds the public tables (VARIANTS, EXTENDED_VARIANTS, STAGE_VARIANTS, WORKLOADS) from it and exposes generate_workload, which generates the Fortran for one workload and variant and returns timing and size metadata. The directory is not part of the installed package. tools/profile_case.py <model> <variant> [--workload W] [--top N] [--out file.prof] [--warm] profiles the generation of one case with cProfile, in a fresh child process by default so that the SymPy cache starts empty. The measurement protocol and the recorded timings are in docs/dev/perf_log.md; profiles are used to find hotspots only, never as timings.
